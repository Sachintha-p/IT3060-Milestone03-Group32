2. Design Progression: Sketches → Wireframes → Low-Fidelity → High-Fidelity
Ideation began with hand-drawn sketches for each of the four flows, comparing paired layout variants before committing to a wireframe. The variants and the rationale for the selected direction are recorded below so the choice can be defended in the viva.
2.1 Design Variants and Justification
Flow 1 — Seat & Room Availability
Variant A: A schematic, floor-plan-style map with tappable seat icons.
Variant B: A grouped list of zones/desks as cards, each carrying a live count and status pill.
Selected: Variant B for the initial release — a true floor-plan renders poorly at mobile widths and needs per-building calibration the group could not maintain at launch. Zone cards surface the same real-time counts (FR-01) at a glance. The floor-plan variant has since been implemented as a secondary view (1.1B Floor Plan View, FR-11), reachable via a List View / Floor Plan toggle, so both variants now coexist rather than being mutually exclusive.
Flow 2 — Reference Book Locator
Variant A: Browse-by-shelf/category tree navigation.
Variant B: A single keyword/title/ISBN search bar returning status-tagged results.
Selected: Variant B. Survey respondents commonly reported a wasted trip for a book they expected to be available; the dominant pain point was catalogue-vs-shelf mismatch, not difficulty 
categorising
 books. A direct search that foregrounds shelf status (FR-02, FR-06) removes the mismatch at the point of decision.
Flow 3 — Staff Operations
Variant A: One combined table listing occupancy rows and book rows together.
Variant B: Three purpose-built views — Dashboard (glance), Update Tool (shelving task), Alerts (exceptions) — on a shared bottom-tab pattern.
Selected: Variant B. Occupancy monitoring is a high-frequency glance task and shelving updates are a periodic, focused task; combining them in one table would force staff to scroll past irrelevant rows for either job.
Flow 4 — Admin Reports & Access
Variant A: A single fixed monthly report with no parameters.
Variant B: A 
parameterised
 report builder (date range, audience/report type) plus a separate detailed-report view with export.
Selected: Variant B. Evidence-based capacity and budget decisions require comparing different date ranges and cohorts rather than one fixed snapshot.

4. Recommendations for Further Refinement
The recommendations below are ordered by the severity of the issue that produced them (Section 3.3). Two items from the previous review have already been implemented in this iteration and are marked accordingly.
High priority — Add a "Continue as Guest" action on 4.1 Login that routes directly to 1.1 Live Map / 2.1 Search, so NFR08's no-login guarantee is visible at the entry point rather than only true once a user is already past it. (Not yet implemented.)
Medium priority — ✅ Implemented this iteration: an explicit, multi-select Zone control was added to 1.2 Filters, separate from Floor, so FR-03 remains fully explicit on floors with more than one zone.
Medium priority — Add a one-tap "Notify me" quick action directly on MISSING rows in 2.1 Search, in addition to the existing 2.2 Book Detail → 2.3 Notify Setup path. (Not yet implemented.)
Low–Medium priority — Give 3.3 Alerts a per-alert "Resolve" control alongside the bulk "Mark All Read", so actioned and pending alerts stay visually distinct. (Not yet implemented.)
Low priority — Wire the audience/report-type pickers in 4.2 Reports Landing to real multi-option dropdowns before the next fidelity pass. (Not yet implemented.)
Future enhancement — ✅ Implemented this iteration: an interactive Floor Plan tile view (1.1B) now sits alongside 1.1 Live Map's zone-card list, reachable via a List View / Floor Plan toggle, exactly as proposed in Section 2.1's Flow 1 variant discussion.
Additional enhancement (not previously recommended, added this iteration) — A full booking lifecycle: QR-code check-in on arrival (1.4 → 1.4B) and an explicit cancel-confirmation step (1.5 → 1.5B), so a reservation can be completed and unwound entirely within the app.
5. Prototyping Tool Justification
The group selected Figma for both the low-fidelity wireframes and the high-fidelity interactive prototype, over alternatives such as Adobe XD, for four reasons: (1) real-time multi-user editing let all four members work on their assigned flow inside one file simultaneously, avoiding version-merge conflicts across a 4-member group; (2) native prototyping links allowed the wireframe stage and the high-fidelity stage to be connected into a navigable flow without exporting to a separate tool, keeping the sketch → wireframe → low-fi → hi-fi progression traceable in one file; (3) reusable components/variants (buttons, status pills, bottom-tab bars) kept all 23 screens visually consistent with a single source of truth; and (4) Figma's free "Starter" tier is sufficient for a student group and the file can be shared as a single project link with comment access for the demonstration/viva.

Appendix B — Reusable Task Script for Recorded Testing
This script lets the group re-run Section 3's sessions on camera with 5 real or proxy participants (including the new T8–T10 tasks) and upload the recordings to the links in Section 7. Read each instruction aloud verbatim to the participant; do not explain the interface beforehand.
Pre-session
Obtain verbal consent to record; confirm the participant's role (student / staff / admin) to assign the matching task set.
Share the Figma prototype in Present mode, starting from 4.1 Login for staff/admin participants or directly from 1.1 Live Map for student/guest participants.
Start the recording and a stopwatch before reading the first task.
During each task
Read the task text from Section 3.1 exactly as written.
Do not correct the participant if they tap the wrong element; let them recover or declare the task failed.
Stop the timer when the participant states they have completed the task (or after 2 minutes, whichever comes first).
Immediately ask the Single Ease Question: "Overall, how difficult or easy was this task?" (1 = very difficult, 5 = very easy).
Note any wrong taps, hesitations, or comments verbatim for the issue log.
Post-session
Thank the participant and stop recording.
Transfer the recording to the shared drive folder, set sharing to "Anyone with the link can view", and paste the link into Section 7.
Log results in the Section 3.2 table format and add any new issues to the Section 3.3 log with a severity rating.
